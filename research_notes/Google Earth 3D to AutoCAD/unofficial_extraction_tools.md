## Key Question 1 — RenderDoc + "Maps Models Importer" (Elie Michel): how it works, breakage history, 2026 status, output

### Takeaway
The RenderDoc/MapsModelsImporter route is a GPU frame-capture hack: RenderDoc is injected into Chrome's GPU process while Google Maps/Earth renders in 3D, the draw calls are saved to an .rdc file, and the Blender add-on rebuilds the meshes and textures from that capture. The original repo's last release is v0.7.0 (5 Apr 2024, RenderDoc 1.31, Blender 4.1); its 2025–2026 issue tracker is a series of unanswered "doesn't work with current Chrome" reports, but a community fork (MapsModelsImporter-Enhanced, v0.5.0, April 2026) claims working support for RenderDoc up to 1.43 and Blender 5.1+. Output is an un-georeferenced pile of texture-per-block mesh chunks in arbitrary scale, explicitly labelled by its author as a non-commercial proof of concept.

### Cited Findings
**What it is / how it works**
- The add-on "imports 3D models and textures captured from Google Maps and Google Earth satellite views into Blender"; the pipeline is (1) RenderDoc injects into Chrome's GPU process to record 3D rendering data, (2) Chrome renders the map and RenderDoc saves an `.rdc` capture, (3) the Blender add-on "parses captured files and reconstructs meshes with materials and textures". Chrome must be launched with the `--disable-gpu-sandbox` flag (plus, since 2024, `--disable_direct_composition=1`). — [eliemichel/MapsModelsImporter README](https://github.com/eliemichel/MapsModelsImporter)
- Author's own framing: "This is a proof of concept showcasing how the 3D render process of Google Maps can be inspected. This is intended for educational purpose only." and "Do not use this for any commercial nor redistribution purpose." The README says private read-only use mirrors ordinary Maps browsing but disclaims responsibility for anything beyond that. — [README](https://github.com/eliemichel/MapsModelsImporter/blob/master/README.md)
- Supported sources beyond Google Maps: "Google Earth web" (added Aug 2020) and "Mapy CZ" (Aug 2020). Linux can import an existing capture but cannot perform the RenderDoc injection step. — [README](https://github.com/eliemichel/MapsModelsImporter/blob/master/README.md)
- The importer works in "blocks" (one mesh + texture per draw-call batch); by default it caps the import at 200 blocks "to prevent Blender from freezing too long"; getting more detail requires a higher screen resolution or browser zoom, which "increase dramatically the number of block[s]". The author recommends his companion add-on LilyTexturePacker to consolidate the "numerous textures" produced. — [add-on README](https://github.com/eliemichel/MapsModelsImporter/blob/master/blender/MapsModelsImporter/README.md)
- Models "import as separate geometry blocks with individual textures, requiring manual cleanup (welding vertices, joining meshes) for practical export workflows." — [repo README summary](https://github.com/eliemichel/MapsModelsImporter)

**Version lock-step with RenderDoc/Chrome and breakage history**
- Release history (each release is pinned to a specific RenderDoc build): v0.3.6 (27 Mar 2021, RenderDoc 1.10, "bugged—avoid"), v0.3.7 (3 Apr 2021, RD 1.10, "Fixed Google Maps import"), v0.4.0/0.4.1 (Jun 2021, RD 1.13, Blender 2.93), v0.5.0-rc1 (30 Apr 2022, RD 1.19, Blender 3.1), v0.5.0 (28 Sep 2023, RD 1.19, Blender 3.1–3.3), v0.6.0–0.6.2 (Feb 2024, RD 1.25, Blender 3.4+), **v0.7.0 (5 Apr 2024, RD 1.31, Blender 4.1)** — the latest release of the original project as of Sep 2026. All releases require Windows. — [Releases](https://github.com/eliemichel/MapsModelsImporter/releases)
- README status notes: "January 2023: only versions 0.5.0 and earlier no longer function due to RenderDoc compatibility issues [RenderDoc could no longer inject into Chrome]; version 0.6.0+ (requiring RenderDoc 1.25 and Blender 3.4) is necessary." and "January 2024: users should add the command-line option `--disable_direct_composition=1` to prevent Chrome from restarting the GPU process." — [README](https://github.com/eliemichel/MapsModelsImporter/blob/master/README.md)
- Open issues in 2025–2026, none with a maintainer reply: #351 (14 Jan 2025) "import .rc file not reading with Blender 3.4 RenderDoc 1.25 MapsModelsImporter-v0.6.2" — scene stays empty; #353 (28 Feb 2025) RDC import not working; #357/#358 (24 Apr 2025) cannot import RDC / no results; #359 (5 May 2025) debug info not generating; **#361 (28 May 2025): Chrome 137.0.7151.56 broke the `--disable_direct_composition=1` workaround — "everytime when injected into the code, chrome will keep refreshing"**; **#365 (26 Dec 2025): "Google Earth stops working with WebGL after enabling RenderDoc" — Chrome shows "Your browser doesn't support WebGL" once RenderDoc is attached**; #366 (13 Jan 2026) asks how to use it with Brave. — [Issues list](https://github.com/eliemichel/MapsModelsImporter/issues); [#351](https://github.com/eliemichel/MapsModelsImporter/issues/351); [#361](https://github.com/eliemichel/MapsModelsImporter/issues/361); [#365](https://github.com/eliemichel/MapsModelsImporter/issues/365)
- GitHub Discussions show the same pattern: "Need Help: Blender import ruins .RDC File Quality" (11 Apr 2025, unanswered), "Is there a possible way to import ... 'Map Base Maps' not Satellite" (2 Jan 2025, unanswered); no 2025–2026 post confirms a working Chrome/RenderDoc combination. — [Discussions](https://github.com/eliemichel/MapsModelsImporter/discussions)
- Community workaround folklore recorded in the tracker: appending `?force=webgl` to the Maps URL for WebGL problems; `--disable_direct_composition=1` since Jan 2024. — [search excerpt of issues #365/#293](https://github.com/eliemichel/MapsModelsImporter/issues/365)

**The 2026 fork that claims it still works**
- "MapsModelsImporter-Enhanced" (Sheep-max) — "Enhanced Blender add-on for importing 3D terrain from Google Maps/Earth. Supports RenderDoc 1.13~1.43, Blender 4.0~5.1+. (For technical research only)". Its comparison table: original v0.4.1 supported RenderDoc 1.13 only / Blender 2.83–3.x; Enhanced v0.5.0 supports RenderDoc 1.13, 1.15, 1.20, 1.23–1.27, 1.30–1.32, 1.43 ("12 versions tested") and Blender 4.0, 4.1, 4.2, 5.0, 5.1+; import time "~446 s → ~30 s (15× faster)"; adds LOD-tier filtering, exact-position de-duplication, and auto-grouping into collections LOD0_Finest…LOD3_VeryCoarse; textures auto-downscaled if over 2048×2048; Windows 10/11 64-bit only; data sources "Google Earth Web, Google Maps 3D". Latest version **v0.5.0 released 2026-04-10** (README) / "April 13" (Releases page). A bundled Chrome launcher has a "Universal" mode (RenderDoc 1.13–1.43, requires Administrator) and a "Legacy" mode (1.13–1.26 only, "non-functional from 1.27+"). — [Sheep-max/MapsModelsImporter-Enhanced](https://github.com/Sheep-max/MapsModelsImporter-Enhanced); [Releases](https://github.com/Sheep-max/MapsModelsImporter-Enhanced/releases)
- The fork's README states there is no georeferencing data documented; "scale/positioning depends on RenderDoc capture data", and it does not document which Chrome versions were tested. Its disclaimer: capturing from Google Maps/Earth "may violate Google's official Terms of Service"; exported models are Google's intellectual property; commercial use is "strictly prohibited"; "Large-scale captures risk account suspension"; RenderDoc files "may contain sensitive browser data and must not be publicly shared". Listed compliant uses: academic research, personal learning, "emergency technical validation (with official data sources)". — [Sheep-max README](https://github.com/Sheep-max/MapsModelsImporter-Enhanced)

**Georeferencing / scale**
- Issue #355 (27 Mar 2025) asks whether the importer can extract "geographic waypoints, geolocation of tiles, bounding box" because the user needs "at least one geolocated point" to place the model, which otherwise lands at Blender's origin (0,0,0) and must be georeferenced afterwards in GIS software. Open, no reply. — [#355](https://github.com/eliemichel/MapsModelsImporter/issues/355)
- Neither the original README nor the add-on README states the units or coordinate frame of the imported model. — [README](https://github.com/eliemichel/MapsModelsImporter/blob/master/README.md); [add-on README](https://github.com/eliemichel/MapsModelsImporter/blob/master/blender/MapsModelsImporter/README.md)

**RenderDoc's own position**
- RenderDoc's README: "RenderDoc is intended for debugging your own programs only. Any discussion of capturing programs that you did not create will not be allowed in any official public RenderDoc setting, including the issue tracker, discord, or via email." It explicitly names "capturing Google Maps or Google Earth" alongside commercial games as disallowed topics (capturing your own Unreal/Unity projects or open-source projects is fine). — [baldurk/renderdoc](https://github.com/baldurk/renderdoc)

### Inferences
- What the popular "Google Earth → Blender" videos (2020–2024) show is almost always this RenderDoc capture: a screen-sized chunk of Google's mesh appears in Blender as dozens–hundreds of texture-per-chunk mesh "blocks" in a camera-relative frame. The capture is limited to what was on screen at the time, so large sites require multiple captures stitched by hand.
- "Did Google break it?" — the evidence shows the breakages were mostly Chrome/RenderDoc platform changes (RenderDoc losing the ability to inject into Chrome in early 2023; Chrome GPU-process restarts in 2024; Chrome 137's handling of the direct-composition flag in May 2025; WebGL being disabled under injection in Dec 2025) rather than a deliberate Google countermeasure; no source found attributes a breakage to a Google-side change. The original author has effectively stopped responding (no maintainer replies on any 2025–2026 issue), so "does it work today" depends on the Enhanced fork, whose April 2026 release is the latest evidence of a working capture (it does not name tested Chrome versions).
- Output is **not georeferenced and not in real-world units**: the geometry is reconstructed from the GPU's clip-space draw calls, so scale, rotation and origin are arbitrary until the user scales/rotates against a known dimension. This makes it the worst of the options for placing homes on a real parcel.

- No source found for a specific 2020 breakage event; the 2020 changes I could document were feature additions (Google Earth web / Mapy CZ support, Aug 2020).

## Key Question 2 — Blosm (formerly blender-osm, vvoovv/prochitecture): "Google 3D Tiles" import

### Takeaway
Blosm's Google 3D Tiles import is the "official-API" route: the user creates a Google Cloud billing account, enables the Map Tiles API, pastes their own key into Blosm, draws an extent in a browser page, and Blosm downloads the Photorealistic 3D Tiles (glTF) and assembles them in Blender at real-world metre scale with a known lat/lon origin. The result is still Google's fused photogrammetry mesh — the wiki says outright "Buildings are not separate objects" — with materials that can't be exported until replaced/baked (baking is Pro-only, ~US$17.80 by search excerpt). Blosm's docs bind the user to Google's Terms of Service and Google Maps Platform Terms, which prohibit extraction and offline storage of Google Maps Content.

### Cited Findings
**What it is, price**
- Blosm: "a few clicks download and import of OpenStreetMap, Google 3D cities and real world terrain data with global coverage." Two editions: a free base version (payment on Gumroad is "completely optional") and a paid Pro version. — [vvoovv/blosm](https://github.com/vvoovv/blosm); [info README](https://github.com/vvoovv/blosm/blob/info/README.md)
- Premium-only features include "One-click baking of multiple textures into a single texture for 3D Tiles", OSM buildings with default materials/tileable textures, forests and single trees as 3D objects, "Satellite imagery and web maps projected on a terrain". The Google 3D Tiles import itself requires "a Google 3D Tiles Key"; the wiki noted "use of Google 3D Tiles in the Preview stage will be free of charge" (dated statement from the API preview period). — [Premium Version wiki](https://github.com/vvoovv/blosm/wiki/Premium-Version)
- Price of the premium version: US$17.80 (search excerpt of the Blender Artists release thread / Gumroad listing; Gumroad page blocked to me). — [Gumroad listing](https://prochitecture.gumroad.com/l/blender-osm) (search excerpt); [Blender Artists thread](https://blenderartists.org/t/blosm-import-of-google-3d-cities-openstreetmap-terrain/608089) (search excerpt)
- A third-party script (chenyingshu/google_3dtile_collection) documents that the **base (free)** Blosm can perform the Google 3D Tiles import and then export OBJ+textures via Blender's exporter. — [google_3dtile_collection](https://github.com/chenyingshu/google_3dtile_collection)
- Wiki home page last edited 31 Oct 2025 (evidence the project is still maintained). — [Blosm wiki](https://github.com/vvoovv/blosm/wiki)

**How the Google import works and what it produces**
- Requirements: "A valid bank card is required to establish a Google Cloud billing account"; users get "1000 imports of Google 3D Tiles for free from Google Maps Platform" per month; enable the Map Tiles API and don't restrict the key. Coverage quoted as "over 2500 cities across 49 countries". — [Import of Google 3D Cities wiki](https://github.com/vvoovv/blosm/wiki/Import-of-Google-3D-Cities)
- Workflow: set the panel to "Google 3D Tiles", press "select" to open a browser page for choosing the extent, paste coordinates back, set the "Geometric error" (detail) value and import. Advice: start with ~1×1 km and the default geometric error (30) because large areas / small error values cause "extremely long download and import times and excessive triangle counts". Example: a 2.3×1.5 km piece of Amsterdam at maximum detail "yielded over 2.5 million triangles across 500+ tiles". — [Import of Google 3D Cities wiki](https://github.com/vvoovv/blosm/wiki/Import-of-Google-3D-Cities); [Import of 3D Tiles wiki](https://github.com/vvoovv/blosm/wiki/Import-of-3D-Tiles)
- Output structure: "By default, each 3D Tile remains a separate Blender object"; "Join 3D Tiles objects" merges all tiles into one object and removes duplicate vertices; **"Buildings are not separate objects"**. — [Import of 3D Tiles wiki](https://github.com/vvoovv/blosm/wiki/Import-of-3D-Tiles)
- A user asked (issue #624, 12 Jun 2025) whether the premium version can "identify which mesh points represent buildings and have each structure separated into individual objects"; the issue is closed (maintainer reply not retrievable to me). — [blosm #624](https://github.com/vvoovv/blosm/issues/624)
- Materials/export: "Imported materials cannot be directly exported"; the add-on provides "Replace Materials" to create export-ready materials (an Image Texture node labelled "BASE COLOR"); textures must be unpacked (File → External Data → Unpack Resources) before exporting to FBX/OBJ; Blender 4.3.2+ recommended because of texture-unpacking bugs in earlier versions; baking many textures into a single image is Pro-only. — [Import of Google 3D Cities wiki](https://github.com/vvoovv/blosm/wiki/Import-of-Google-3D-Cities); [Import of 3D Tiles wiki](https://github.com/vvoovv/blosm/wiki/Import-of-3D-Tiles)

**Georeferencing**
- Blosm scenes are georeferenced by custom scene properties `_lat_` and `_lon_` (origin of the local coordinate system) plus optional `_heading_`; conversion uses a Transverse Mercator projection (`transverse_mercator.py`) with `fromGeographic(lat, lon)` and `toGeographic(x, y)` helpers. — [Georeferenced Blender Scene wiki](https://github.com/vvoovv/blosm/wiki/Georeferenced-Blender-Scene)
- All measurements are in metres; terrain (SRTM) resolution "about 30 meter"; custom projections via the optional `bpyproj` add-on (EPSG codes / PROJ strings) "works only in Blender 2.8x due to external dependencies". — [Documentation wiki](https://github.com/vvoovv/blosm/wiki/Documentation)
- "Relative to initial import" positions later imports (e.g., Google tiles after OSM/terrain) relative to the first import rather than Blender's origin, so successive datasets align. — [Import of Google 3D Cities wiki](https://github.com/vvoovv/blosm/wiki/Import-of-Google-3D-Cities)
- Google serves the tiles in ECEF (EPSG:4978, Earth-centred) coordinates; loaders/downloaders re-centre and rotate "geodetic Up → +Y" for DCC use. — [voxelearth/nodejs-3dtiles-downloader](https://github.com/voxelearth/nodejs-3dtiles-downloader); [QGIS docs (EPSG:4978 only)](https://github.com/qgis/QGIS-Documentation/blob/master/docs/user_manual/working_with_3d_tiles/3d_tiles.rst)

**Terms of service**
- The Blosm wiki states that using Google 3D Tiles binds the user to "Google's Terms of Service", "Google Maps Platform Terms of Service" and "Google Privacy Policy"; the chenyingshu script repeats the same three-document binding. Neither Blosm's README nor its wiki contains a warning about extraction/offline-use clauses. — [Import of Google 3D Cities wiki](https://github.com/vvoovv/blosm/wiki/Import-of-Google-3D-Cities); [google_3dtile_collection](https://github.com/chenyingshu/google_3dtile_collection)
- Blosm's Google import is one of several key-based downloaders; the relevant Google restrictions are in Key Question 7 (Maps Platform ToS 3.2.3 "No Scraping / No Caching / No Creating Content"; Map Tiles API policy "not extracted, traced, or otherwise derived… from Photorealistic 3D Tiles"; "offline uses" not allowed). — see KQ7.

### Inferences
- Blosm is the only one of the tools surveyed that gives an output that is both metre-scaled and anchored to a known lat/lon (via `_lat_`/`_lon_`). It is "georeferenced" only in the sense of a local Transverse Mercator frame centred on the scene origin; to land in an AutoCAD drawing on a State Plane / UTM grid, the user must transform from that local TM origin to the drawing's CRS (or place the mesh by hand against a surveyed point). Nothing in Blosm's docs describes exporting to a projected CRS directly.
- Because the API-key route downloads and keeps the tiles inside a .blend, it is (paradoxically) the route whose ToS exposure is clearest: the key-holder is a "Customer" under the Maps Platform terms and the download/keep/derive behaviour maps directly onto the 3.2.3 prohibitions (see KQ7). The RenderDoc route has no contract with Maps Platform but still falls under Google's consumer terms.

- Could not verify the US$17.80 price or the current Blosm version number directly (Gumroad and Blender Artists blocked; GitHub commit/release feeds blocked by the session proxy).
- Maintainer's answer in issue #624 (buildings separable?) could not be retrieved; the wiki's "Buildings are not separate objects" is taken as authoritative.
- No statement from vvoovv on commercial use of Google-tile imports was found.

## Key Question 3 — Other 3D Tiles downloaders/converters, QGIS, Google Earth Decoder (MSFS), Earth Studio

### Takeaway
A cluster of small open-source scripts (3dtiles-dl, nodejs-3dtiles-downloader, google-earth-as-gltf, google_3dtile_collection) do what Blosm does without Blender: walk Google's `root.json` tileset with the user's API key and save the leaf `.glb` tiles, re-centred from ECEF. They are mostly one-weekend projects last touched in 2023–2024. Cesium's `3d-tiles-tools` converts formats but does not download from Google. QGIS 3.34+ can stream Google tiles for viewing/styling but its docs describe no export of a tiled-scene layer. The flight-sim "Google Earth Decoder" (a different, older technique that pulls Google Earth's proprietary "rocktree" data without an API key) broke in 2025 when Google changed the imagery epoch and was binary-patched back to life in 2026. Earth Studio exports camera paths and track points, not geometry, and Google says it is not licensed for commercial work.

### Cited Findings
**Key-based Google 3D Tiles downloaders**
- lukaslaobeyer/3dtiles-dl — "Download 3d tiles from Google Maps"; needs an API key (`-k`), takes lon/lat in degrees plus a radius in metres, exports glTF that "can, for example, be imported into Blender"; includes a `/blender` folder; all three commits are dated 16 Oct 2023; no ToS disclaimer in README. — [3dtiles-dl](https://github.com/lukaslaobeyer/3dtiles-dl); [commits](https://github.com/lukaslaobeyer/3dtiles-dl/commits/master)
- voxelearth/nodejs-3dtiles-downloader (a fork of 3dtiles-dl) — "Super fast downloader for 3D tiles from Google Photorealistic 3D Tiles and optionally convert from ECEF to ENU"; requires a Maps Platform key with the 3D Tiles API enabled; converts lat/lng to ECEF, traverses `.../v1/3dtiles/root.json`, culls by sphere intersection, downloads leaf `.glb` files, then "recenters to a shared origin, rotates geodetic Up → +Y, bakes rotation/scale into vertex data" so root nodes are translation-only; README: "Ensure your usage complies with Google's Terms of Service." — [nodejs-3dtiles-downloader](https://github.com/voxelearth/nodejs-3dtiles-downloader)
- OmarShehata/google-earth-as-gltf — web app demonstrating "how to fetch 3D Tiles from the Google Photorealistic API and how to correctly normalize & rotate the glTF tiles, or combine a set of them into one glTF"; uses loaders.gl to traverse the tileset for a lat/lng/zoom, normalises from ECEF to a (0,0,0)-centred frame, offers screen-space-error (SSE) selection (min 1 = highest quality); README states **"Offline use is prohibited" per Google's Map Tiles API policies** and calls it an educational tool; last commit 10 Feb 2024. — [google-earth-as-gltf](https://github.com/OmarShehata/google-earth-as-gltf); [commits](https://github.com/OmarShehata/google-earth-as-gltf/commits/main)
- chenyingshu/google_3dtile_collection — "Use Google Tile API to download models to Blender and export as OBJ file"; wraps the free Blosm base import, then exports OBJ + textures with an optional `objuvpacker.py` to merge textures into one material; recommends 0.3–1.0 km bounding boxes; repeats Google's three-ToS binding. — [google_3dtile_collection](https://github.com/chenyingshu/google_3dtile_collection)
- Commercial Blender add-on "Tile Importer" is sold on BlenderKit and Fab as "lets users import Google Maps 3D Tiles into Blender directly using the Google Maps API" (search excerpt; both listings blocked to me). — [BlenderKit listing](https://www.blenderkit.com/addons/b62311af-f1bc-43d8-845a-cdd313f32dbe/); [Fab listing](https://www.fab.com/listings/39d8cce7-1fbe-41b9-960f-4d3f379e60d7?lang=en)

**Cesium 3d-tiles-tools**
- "A collection of tools and utilities for converting, optimizing, processing, and analyzing 3D Tiles data": gzip/ungzip, combine/merge tilesets, upgrade legacy tilesets, and content conversion among GLB, B3DM, I3DM, PNTS, CMPT (e.g., `b3dmToGlb`, `convertB3dmToGlb`, `glbToB3dm`), plus Draco optimisation via gltf-pipeline. The README does not mention downloading from Google or any remote service — it works on local tiles. — [CesiumGS/3d-tiles-tools](https://github.com/CesiumGS/3d-tiles-tools)

**QGIS**
- QGIS's 3D Tiles support (added in 3.34, Nov 2023, funded by a Cesium Ecosystem Grant) supports 3D Tiles 1.0 b3dm and 3D Tiles 1.1 glTF content; "currently only tilesets using EPSG:4978 are supported"; Google "Photorealistic 3D Tiles" is listed among cloud data sources. The user-manual page describes adding, styling (textured or wireframe) and viewing; it contains no export/save-as capability for tiled-scene layers. — [QGIS-Documentation 3d_tiles.rst](https://github.com/qgis/QGIS-Documentation/blob/master/docs/user_manual/working_with_3d_tiles/3d_tiles.rst); [QGIS 3.44 manual](https://docs.qgis.org/3.44/en/docs/user_manual/working_with_3d_tiles/3d_tiles.html) (search excerpt)
- Google's photorealistic tiles can be loaded through the Cesium ion QGIS plugin published alongside 3.34 (search excerpt). — [North Road, 7 Nov 2023](https://north-road.com/2023/11/07/qgis-3d-tiles-thanks-to-cesium-ecosystem-grant/) (search excerpt); Cesium later announced a 3D globe view in QGIS (20 Jun 2025). — [Cesium blog](https://cesium.com/blog/2025/06/20/3d-globe-view-now-available-in-qgis/) (title only)

**Google Earth Decoder / GEDOT (flight-sim community) — a non-API, non-RenderDoc technique**
- "Google Earth Decoder" is a Windows tool (author credited as Reddit user "u/Jonahex111") that "retrieves city sceneries from Google Earth" and outputs glTF tiles that Thalixte's Google Earth Decoder Optimization Tools (GEDOT, Python/Blender scripts) turn into Microsoft Flight Simulator scenery packages; GEDOT can "update the position of the MSFS scenery tiles" with "latitude correction and/or longitude correction"; 464 commits; no legal disclaimer in its README. — [Thalixte/Google-Earth-Decoder-Optimization-Tools](https://github.com/Thalixte/Google-Earth-Decoder-Optimization-Tools)
- The underlying method traces to retroplasma/earth-reverse-engineering — "Reversing Google's 3D satellite mode": it downloads Google Earth's octree-based "rocktree" octants and exports OBJ (packed XYZ, UVs, normals) — that repository was **archived (read-only) on 14 Aug 2022**. — [retroplasma/earth-reverse-engineering](https://github.com/retroplasma/earth-reverse-engineering)
- 2025–2026 status (search excerpts; flightsim.to blocked to me): "Since around July 2025, when launching Google Earth Decoder, a warning message such as 'Invalid Credentials...' has been displayed"; "Recent Google backend changes caused issues, specifically requiring the imagery epoch to be updated to version 1012"; a community release "Google Earth Decoder/Earth2msfs Fixed 2026" ships a DLL "binary-patched to use the active imagery epoch version 1012 (0x3F4), restoring connection and metadata downloads from Google's servers". — [flightsim.to "Fixed 2026"](https://flightsim.to/addon/112579/google-earth-decoder-earth2msfs-fixed-2026); [flightsim.to "2026 update"](https://flightsim.to/addon/111678/google-earth-decoder-2026-update); [GEDOT on blender-addons.org](https://blender-addons.org/google-earth-decoder-optimization-tools/)

**Google Earth Studio**
- Earth Studio's "3D Camera Export" (File → Export → 3D Tracking Data) exports the 3D camera and Track Points (as nulls) for Adobe After Effects; community add-ons import that JSON into Blender for camera match-moving with rendered image sequences — i.e., it exports camera motion + images, not terrain/building geometry. — [Earth Studio docs: 3D Camera Export](https://earth.google.com/studio/docs/advanced-features/3d-camera-export/) (search excerpt); [imagiscope/Blender_GES_Import](https://github.com/imagiscope/Blender_GES_Import); [SolarLiner/blender_io_earth_studio](https://github.com/SolarLiner/blender_io_earth_studio)
- Earth Studio FAQ (search excerpt): "Google currently does not offer a license to use Google Earth imagery for commercial applications"; content "may not be used for promotional films, advertisements or commercials"; attribution must be on screen for the duration and is watermarked automatically on each rendered frame; permitted uses listed as research, education, film and nonprofit. — [Earth Studio FAQ](https://www.google.com/earth/studio/faq/) (search excerpt); [Google Earth Community thread on non-commercial use](https://support.google.com/earth/thread/350390104/clarification-on-non-commercial-use-of-google-earth-studio-content?hl=en) (title)

### Inferences
- Three distinct data paths exist and it matters which one a video is using: (a) GPU capture of the browser (RenderDoc) — no key, screen-limited, un-georeferenced; (b) Map Tiles API download with the user's own key (Blosm, 3dtiles-dl, etc.) — georeferenceable (ECEF → local metres), area-limited only by quota/patience, contractually bound by Maps Platform terms; (c) direct scraping of Google Earth's internal rocktree protocol (retroplasma / Google Earth Decoder) — no key, georeferenced by octant, but dependent on undocumented endpoints that Google altered in 2025 (epoch change) and whose reference implementation was archived in 2022.
- QGIS is a viewer for this purpose: it can display Google tiles next to parcel data but there is no documented way to write the streamed mesh to a local file, so it is not an extraction tool.
- Earth Studio is not an extraction route at all; it is relevant only for producing georegistered camera moves/renders for compositing.

## Key Question 4 — Older techniques: SketchUp "Add Location" with Google data, 3D Warehouse buildings, screenshot photogrammetry

### Takeaway
SketchUp's Google era ended in stages: Trimble bought SketchUp on 1 June 2012 with five years of free Google geo-data; Google retired Building Maker (1 Jun 2013) and the user-generated 3D-Warehouse-to-Earth pipeline (1 Oct 2013) in favour of auto-generated mesh; and Add Location switched from Google to DigitalGlobe/Trimble data with SketchUp 2017 because Google's APIs do not allow the imagery/terrain to be stored inside a file. Screenshot photogrammetry (feeding many Google Earth screen grabs to SfM software) demonstrably produces plausible meshes (Chen & Clarke 2016 report planimetric error ≤1% and vertical ≤5% in urban tests) but is subject to the same non-extraction terms.

### Cited Findings
**SketchUp / Google**
- "Trimble Navigation acquired SketchUp from Google on June 1, 2012. As part of that transition, Google agreed to give Trimble free geo data for 5 years"; Google has "since deprecated their entire geo-modeling program"; the core constraint was that "Google's APIs do not give away their data for modification which is what the Add Location feature requires, as SketchUp's Add Location requires that the imagery and other data be imported into and stored inside the SKP file." (search excerpts of SketchUp staff/community posts). — [SketchUp forum: Upcoming Change to Add Location](https://forums.sketchup.com/t/upcoming-change-to-add-location/40953/248) (search excerpt)
- "SketchUp Pro 2017 offered satellite imagery from DigitalGlobe and terrain data from data that Trimble already possessed"; Pro users got "DigitalGlobe Satellite" and "Trimble Map" layers; Make users got only the OSM-based "Trimble Map"; "Google Satellite remained as the default layer for a few more weeks" after 2017 shipped (search excerpts). — [SketchUp forum thread p.3](https://forums.sketchup.com/t/upcoming-change-to-add-location/40953?page=3) (search excerpt); [Sketchucation: Geolocation 3D toggle removed](https://sketchucation.com/forums/viewtopic.php?f=15&t=67708) (title)
- Users complained that "the quality provided through the OpenStreetMap and Digital Globe content is too poor quality compared to what was previously available" from Google (search excerpt). — [Graphisoft community post](https://community.graphisoft.com/t5/Collaboration-with-other/Trimble-destroyed-Sketchup-Archicad-needs-native-Google-Earth/td-p/265056) (search excerpt)

**3D Warehouse → Google Earth buildings**
- Google's announcement: "User generated 3D model pipeline has been retired October 1st, 2013"; "no models were removed from the Trimble 3D Warehouse"; existing accepted models were processed and published in a final push, after which Google relied on "automatically generated 3D imagery from aerial photography" (search excerpts). — [3dwh Google Group announcement](https://groups.google.com/g/3dwh/c/epXUQA2bJ2s); [Google Earth Blog, Aug 2013](https://www.gearthblog.com/blog/archives/2013/08/google-continues-to-expand-3d-imagery.html)
- Google Building Maker "was retired on June 1, 2013". — [Wikipedia: Google Building Maker](https://en.wikipedia.org/wiki/Google_Building_Maker) (search excerpt)

**Screenshot photogrammetry (Google Earth screen grabs → SfM)**
- Chen & Clarke, "Rapid 3D Modeling Using Photogrammetry Applied to Google Earth", AutoCarto 2016 (Albuquerque, 14–16 Sep 2016): examined "the feasibility of using screen images of Google Earth's proprietary high-resolution 3D models in creating point cloud and textured mesh models using structure-from-motion (SfM) in Tokyo, Japan, and UCSB and Mount Herard, Colorado"; SfM "succeeded in creating models for all three locations that visually resembled Google Earth's own models", worked best in built-up areas and "struggled with the natural environment of Mount Herard"; "planimetric errors of 1% or less and vertical errors of 5% or less for Tokyo and UCSB" when comparing sample distances against Google Earth itself (search excerpts; PDF blocked). — [Chen & Clarke 2016 PDF](https://www.cartogis.org/docs/proceedings/2016/Chen_and_Clarke.pdf) (search excerpt); [Semantic Scholar entry](https://www.semanticscholar.org/paper/Rapid-3D-Modeling-Using-Photogrammetry-Applied-to-Chen-Clarke/1fded1033bf18601cbbbd99bea21f70dc0b60afb)
- A Civil Engineering Journal study integrating smartphone photos with Google Earth images reports "a mean accuracy level of less than 5 meters compared with DSLR camera results" (search excerpt). — [Civil Engineering Journal article](https://civilejournal.org/index.php/cej/article/view/1980) (search excerpt)
- Other papers on the same idea: "Printgrammetry — 3-D Model Acquisition Methodology From Google Earth Imagery Data" and "A Photogrammetric Method for Spatial Data Extraction from Google Earth and Improvement with Precision Analysis" (titles only). — [Printgrammetry](https://www.researchgate.net/publication/341714846_Printgrammetry-3-D_Model_Acquisition_Methodology_From_Google_Earth_Imagery_Data); [Photogrammetric method](https://www.researchgate.net/publication/324932557_A_Photogrammetric_Method_for_Spatial_Data_Extraction_from_Google_Earth_and_Improvement_with_Precision_Analysis)
- Note the accuracy figures above are relative to Google Earth's own model, not to ground survey: they measure how well SfM reproduces Google's mesh, and inherit whatever error Google's mesh already has (see KQ5).

### Inferences
- The pre-2012 SketchUp workflow people remember ("Add Location pulls Google terrain and imagery into my model") is gone precisely because Google would not license the data to be stored in a file — the same policy that underlies the restrictions on today's extraction tools.
- Screenshot photogrammetry is "allowed" only in the sense that nobody needs a hack to take screenshots; the output is a derivative 3D model of Google content, which is what the Maps Platform and Earth terms forbid (KQ7). Its practical quality is lower than the direct mesh routes because it is re-photogrammetry of an already photogrammetric surface (double smoothing), and it is un-georeferenced unless the user scales/aligns it.

## Key Question 5 — Quality reality check: what Google's photorealistic mesh is, its accuracy, and fitness for site planning

### Takeaway
Every route above yields the same product: Google's auto-generated photogrammetry surface — one continuous textured skin over terrain, buildings and trees, with no semantic separation, no parcel lines, no interiors, and texture baked into thousands of small images. Blosm's docs state "Buildings are not separate objects"; a 2.3×1.5 km area at full detail is ~2.5 M triangles across 500+ tiles. No published Google accuracy specification was found; the best available evidence is user-measured discrepancies (e.g., Everest reading ~8,700 m vs 8,849 m in the tiles; 3D models "sink into the earth" without height correction). This is fine for context/massing visuals and rough vertical context, not for boundaries, grading or placing a house to setback tolerances.

### Cited Findings
- Blosm: "Buildings are not separate objects" in imported 3D Tiles; tiles are separate objects or can be joined into one with duplicate vertices removed. — [Import of 3D Tiles wiki](https://github.com/vvoovv/blosm/wiki/Import-of-3D-Tiles)
- Density: Amsterdam 2.3×1.5 km at maximum detail = "over 2.5 million triangles across 500+ tiles"; start with ~1×1 km at geometric error 30 to avoid "excessive triangle counts". — [Import of Google 3D Cities wiki](https://github.com/vvoovv/blosm/wiki/Import-of-Google-3D-Cities)
- Textures: 3D Tiles imports "use multiple textures that cannot be exported directly" until materials are replaced or baked (Pro). — [Import of 3D Tiles wiki](https://github.com/vvoovv/blosm/wiki/Import-of-3D-Tiles)
- RenderDoc route: geometry arrives as per-draw-call "blocks" (default cap 200) with one texture each; the Enhanced fork sorts them into LOD collections from LOD0_Finest to LOD3_VeryCoarse and de-duplicates by position, and downsizes textures over 2048 px — i.e., the capture mixes several levels of detail depending on distance from the camera. — [add-on README](https://github.com/eliemichel/MapsModelsImporter/blob/master/blender/MapsModelsImporter/README.md); [Sheep-max README](https://github.com/Sheep-max/MapsModelsImporter-Enhanced)
- Google's 3D Tiles are streamed as a level-of-detail hierarchy chosen by screen-space error; lower SSE (min 1) = higher quality, higher SSE = coarser tiles over wider areas. — [google-earth-as-gltf](https://github.com/OmarShehata/google-earth-as-gltf)
- Altitude accuracy questions raised by Cesium users: "Mt Everest measuring at only 8,700 m when it should measure 8,849 m" in the Photorealistic tiles; 3D models "sink into the earth when Google's Photorealistic 3D Tileset is activated", prompting height-correction workarounds (search excerpts; threads blocked). — [Cesium Community: How accurate are Google Photorealistic 3D Tiles altitudes?](https://community.cesium.com/t/how-accurate-are-google-photorealistic-3d-tiles-altitudes/30155) (search excerpt); [Cesium Community: height correction](https://community.cesium.com/t/googles-photorealistic-3d-tiles-height-correction/32666) (search excerpt)
- Google Maps Platform itself frames Photorealistic 3D Tiles as a visualisation layer and says you may overlay your own 3D objects only "as long as the 3D objects aren't extracted, traced, or otherwise derived by hand or machine from Photorealistic 3D Tiles" — i.e., Google does not offer it as measurable geodata (search excerpt). — [Map Tiles API Policies](https://developers.google.com/maps/documentation/tile/policies) (search excerpt)
- For the 2D imagery under Google Earth (not the mesh), a peer-reviewed study found horizontal positional accuracy of 39.7 m RMSE overall (range 0.4–171.6 m) relative to Landsat GeoCover, 22.8 m RMSE for satellite-derived and 41.3 m RMSE for aerial-derived points (older global sample; illustrates that Google's geo-registration is not survey-grade). — [Horizontal Positional Accuracy of Google Earth's High-Resolution Imagery Archive (PMC)](https://www.ncbi.nlm.nih.gov/pmc/articles/PMC3791001/)
- Screenshot-SfM re-creations of Google's mesh match it to within ~1% planimetric / ~5% vertical (relative to Google, not ground truth). — [Chen & Clarke 2016](https://www.cartogis.org/docs/proceedings/2016/Chen_and_Clarke.pdf) (search excerpt)
- Market signal: vendors sell "clean architectural site data with properly placed 3D buildings and accurate height data, requiring no manual cleanup unlike other data sources" specifically because Google's automated mesh "doesn't meet professional architectural standards for site plans and CAD work" (vendor marketing; search excerpt). — [CAD ATLAS](https://cad-atlas.com/) (search excerpt)
- Architects on Google's own 3D-modelling group have long noted the automated models are not suitable for planning/permitting workflows (search excerpt). — [3dwh group thread](https://groups.google.com/g/3dwh/c/Ym0OuV8ONOc) (search excerpt)

### Inferences
- Geometric error budget: Google publishes no accuracy spec for the mesh; combining (a) the user-observed multi-tens-of-metres altitude discrepancy on Everest (extreme terrain), (b) the ellipsoid-vs-orthometric height confusion that causes "sinking" models, and (c) decimetre-to-metre-level smoothing typical of aerial-oblique photogrammetry at Google's GSD, a designer should assume metre-level positional uncertainty and worse on roof edges, eaves, trees and ground under canopy — not the 0.1–0.3 ft class of a boundary/topo survey or airborne lidar DEM.
- "Melted" look: because the surface is a single fused skin, building walls flare into the ground, overhangs are filled, vegetation is blobbed, and there are no crisp edges to snap to in CAD. Nothing in the mesh identifies a parcel boundary, easement, setback, utility or finished-floor elevation.
- Fitness: adequate for a massing/context backdrop or a rendering, and to sanity-check rough slopes; inadequate for site plans, grading, drainage, setbacks, or any drawing that will be submitted or relied upon. Any real placement of homes needs a survey (boundary + topo) and/or public lidar, with the Google mesh at most as a visual overlay.

### Gaps
- No authoritative, quantitative accuracy assessment of Google's Photorealistic 3D Tiles against survey/lidar control was found (search budget exhausted; Cesium threads blocked). The report should state that no Google accuracy specification exists rather than quote a number.
- Google's own 3D Tiles overview/FAQ pages (which describe how the mesh is produced from aerial imagery) were blocked; the description of the mesh's nature is corroborated by Blosm's docs and the tools' READMEs rather than Google's page.

## Key Question 6 — Getting the mesh into AutoCAD (Blender → DXF, OBJ/FBX routes, 3ds Max/ReCap/Navisworks, SketchUp, decimation, units/georeferencing)

### Takeaway
There is no clean native path: AutoCAD's IMPORT command does not read OBJ, FBX or glTF (FBXIMPORT was removed in AutoCAD 2019), so users either export DXF from Blender (the DXF exporter is a "limited support" legacy extension since Blender 4.2 that writes meshes as 3DFACE/POLYFACE entities), use a paid AutoCAD plugin such as Automesher (or the free Mesh-In) to read OBJ/STL directly, or route through 3ds Max → DWG. A multi-million-triangle textured mesh must be heavily decimated first, textures are lost or irrelevant in AutoCAD, and the result carries no coordinate system unless it came from Blosm (local TM origin) and is transformed/moved to the drawing's grid by the user.

### Cited Findings
**AutoCAD import formats**
- "AutoCAD by default does not support direct import of STEP, SKP, OBJ, or IFC files without conversion"; the Automesher application adds `AmImportMesh`/`AmExportMesh` commands for 30+ formats including OBJ, STEP, IGES, SKP, FBX, 3DM, DAE, SAT, STL, IFC (vendor pages; search excerpts). — [Automapki: Import STEP, STL, OBJ, 3DM & SKP to AutoCAD](https://www.automapki.com/tutorials/import-step-stl-obj-3dm-skp-and-other-3d-files-in-autocad.html) (search excerpt); [Automapki: AutoCAD 3D Import & Export](https://www.automapki.com/news/import-export-3d-files.html) (search excerpt)
- Freeware alternative: "For importing 3D models in mesh formats STL, OBJ, 3DS and OFF, you can use freeware application Mesh-In by loading it into AutoCAD using APPLOAD and typing the MESHIN command" (search excerpt). — [CAD Forum tip 14072](https://www.cadforum.cz/en/how-to-import-an-stl-obj-or-3ds-file-to-an-autocad-3d-model-tip14072) (search excerpt)
- "Autodesk removed the ability to import FBX file formats into AutoCAD starting with the 2019 release, removing the FBXIMPORT command"; Autodesk's guidance is to move data between AutoCAD and 3ds Max as DWG instead (search excerpts). — [House of BIM: 2019 AutoCAD R.I.P. FBXIMPORT](https://www.houseofbim.com/posts/2019-autocad-r-i-p-fbximport/) (search excerpt); [Autodesk: How to transfer files and data from AutoCAD to 3ds Max](https://www.autodesk.com/support/technical/article/caas/sfdcarticles/sfdcarticles/How-to-transfer-files-and-data-from-AutoCAD-to-3ds-Max.html) (search excerpt)
- 3ds Max can export scenes to AutoCAD DWG (so Blender → FBX/OBJ → 3ds Max → DWG is a working, if lossy, chain). — [3ds Max 2023 help: Exporting to AutoCAD DWG Files](https://help.autodesk.com/view/3DSMAX/2023/ENU/?guid=GUID-59E8ED62-1BB1-44A7-97D3-35065D389B5C) (title; page blocked)

**Blender DXF exporter status**
- Blender bundled add-ons only up to 4.1; from 4.2 LTS the DXF importer and exporter live on the Extensions Platform, each labelled "This extension was part of Blender 4.1 bundled add-ons. It is now offered as it is, with limited support." (search excerpts). — [Export Autocad DXF Format (.dxf) — Blender Extensions](https://extensions.blender.org/add-ons/export-autocad-dxf-format-dxf/) (search excerpt); [Import AutoCAD DXF — Blender Extensions](https://extensions.blender.org/add-ons/import-autocad-dxf-format-dxf/) (search excerpt)
- Exporter behaviour (Blender manual, 3.6): "polyline-mode activates a complex representation where objects export to POLYLINEs (curves) and POLYFACEs (meshes), otherwise exporting to common LINEs and 3DFACEs"; a global Scale parameter is provided (search excerpt). — [Blender Manual: AutoCAD DXF](https://docs.blender.org/manual/en/3.6/addons/import_export/scene_dxf.html) (search excerpt)
- Open bug reports against the exporter include "Export Autocad DXF Format (.dxf) does not create .dxf file" (#102478), layer/colour export defects (#105302) and "Wont Export my DXF Import" (#99717) (titles). — [#102478](https://projects.blender.org/blender/blender-addons/issues/102478); [#105302](https://projects.blender.org/blender/blender-addons/issues/105302); [#99717](https://projects.blender.org/blender/blender-addons/issues/99717)

**Units, scale, georeferencing, decimation**
- Blosm output is in metres with a stored `_lat_`/`_lon_` origin in a Transverse Mercator frame; converting Blender x,y back to lat/lon is via `projection.toGeographic(x, y)`. — [Georeferenced Blender Scene wiki](https://github.com/vvoovv/blosm/wiki/Georeferenced-Blender-Scene); [Documentation wiki](https://github.com/vvoovv/blosm/wiki/Documentation)
- RenderDoc captures carry no geolocation (issue #355 unanswered; fork README: no georeferencing data). — [#355](https://github.com/eliemichel/MapsModelsImporter/issues/355); [Sheep-max README](https://github.com/Sheep-max/MapsModelsImporter-Enhanced)
- Raw Google tiles are in ECEF (EPSG:4978); downloaders re-centre to a local origin and rotate up-vector before Blender import. — [nodejs-3dtiles-downloader](https://github.com/voxelearth/nodejs-3dtiles-downloader); [QGIS docs](https://github.com/qgis/QGIS-Documentation/blob/master/docs/user_manual/working_with_3d_tiles/3d_tiles.rst)
- Triangle counts of 2.5 M for ~3.5 km² at full detail (Blosm) and the 200-block default cap (RenderDoc) show why decimation/LOD selection is required before CAD. — [Import of Google 3D Cities wiki](https://github.com/vvoovv/blosm/wiki/Import-of-Google-3D-Cities); [add-on README](https://github.com/eliemichel/MapsModelsImporter/blob/master/blender/MapsModelsImporter/README.md)
- Blosm materials must be replaced/unpacked before FBX/OBJ export; the chenyingshu script consolidates textures into a single material for OBJ. — [Import of 3D Tiles wiki](https://github.com/vvoovv/blosm/wiki/Import-of-3D-Tiles); [google_3dtile_collection](https://github.com/chenyingshu/google_3dtile_collection)

### Inferences
- Practical chains seen in tutorials: (1) Blender → DXF (3DFACE mesh) → AutoCAD (huge files, thousands of faces per tile, no textures, exporter flaky since 4.2); (2) Blender → OBJ/STL → AutoCAD via Automesher/Mesh-In (mesh object in DWG; textures dropped); (3) Blender → FBX → 3ds Max → DWG (keeps materials in Max but AutoCAD still shows an untextured mesh); (4) Blender → OBJ/DAE → SketchUp → DWG (SketchUp Pro exports DWG but chokes on multi-million-face meshes). In all four, AutoCAD receives an untextured polyface mesh that cannot be snapped to reliably and is not a surface/TIN usable by Civil 3D grading tools without further conversion.
- For placing homes on a parcel, the key missing ingredient is coordinates: only a Blosm-derived mesh can be placed by computing the local TM origin's lat/lon into the drawing's State Plane/UTM grid (an extra transform step the user must script or do in QGIS/Civil 3D); a RenderDoc mesh must be scaled from a known dimension and aligned by eye to survey linework.

### Gaps
- Autodesk's official IMPORT-format list page was blocked; the "no native OBJ/FBX/glTF" statement rests on Autodesk/third-party pages surfaced as search excerpts (consistent across sources).
- Could not confirm Automesher's current price or the 2026 status of Mesh-In.
- No documented example was found of anyone bringing a Google mesh into Civil 3D as a surface; the report should not claim that path works.

## Key Question 7 — Legal / terms-of-service exposure (Maps Platform ToS, Map Tiles API policy, Google Earth/Maps consumer terms, RenderDoc), enforcement history, practical risk for private concept work vs published/sold work

### Takeaway
Extracting Google's 3D mesh breaches Google's contracts on every route: the Maps Platform Terms (binding on anyone using an API key, i.e., Blosm/3D-Tiles downloaders) prohibit exporting, extracting, scraping, pre-fetching, storing or caching Google Maps Content and creating content/derivative works from it; the Map Tiles API policy specifically forbids 3D objects "extracted, traced, or otherwise derived by hand or machine from Photorealistic 3D Tiles" and "offline uses"; Google Earth/Earth Studio content is not licensed for commercial use; and the tool authors themselves (Michel, Sheep-max, RenderDoc's Karlsson) say so. The only evidence of Google enforcement is a fuzzy itch.io report of a DMCA notice; no lawsuit or documented action against an individual for private use was found, and flight-sim forums' working rule is "personal use on your own PC is tolerated, distributing/selling is not". For a real property-development design the realistic exposure is contractual (API-key account suspension/termination) plus copyright/derivative-work claims if the model is published, sold, or submitted — and, separately, professional-liability exposure from relying on non-survey data.

### Inferences
- Which terms bite, by route: (a) Blosm / key-based downloaders: a direct breach of Maps Platform §3.2.3(a) (extract/store/bulk download), (b) (cache), (c) (create content from Google Maps Content) and of the Map Tiles policy's derived-3D-object and offline-use bans; consequence under the same contract is suspension/termination of the Google Cloud project/account (and Google can require a compliance review of the application, §3.2.2(c)). (b) RenderDoc / rocktree scraping / screenshot-SfM: no Maps Platform contract, but the consumer Google Terms plus the Maps/Earth Additional Terms govern, Google keeps copyright in the imagery/mesh (Google and its providers, e.g., Airbus/Maxar), and the output is a derivative work; the Earth Studio FAQ shows Google's stated position that Earth content is not licensed for commercial use at all. (c) Any route: if the model is redistributed (published renders are tolerated only with attribution for Earth content; distributing the mesh itself is not), the exposure becomes copyright (DMCA/takedown) rather than only contract.
- Practical risk gradient for a land-development concept: private, unpublished use on one's own machine has produced no documented enforcement and is what the tool authors call "read-only consumption"; using the mesh in a client deliverable, marketing render, planning submission or sold scenery is the case every author and forum flags as prohibited, and it also creates professional-liability exposure because the data has no accuracy specification (KQ5). A design professional submitting drawings derived from an unlicensed, un-specified dataset risks both a copyright/ToS claim and a negligence argument if the site geometry is wrong.
- The legitimate alternatives implied by the terms: (1) view/overlay only — keep Google 3D Tiles as a streamed backdrop in a compliant viewer (Cesium/QGIS/Maps 3D) and model your own buildings on top without tracing; (2) buy licensable data (Nearmap/Maxar/Vexcel meshes, municipal open 3D-Tiles/CityGML, USGS 3DEP lidar); (3) commission a survey/drone photogrammetry.
