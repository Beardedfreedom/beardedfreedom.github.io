## Cross-cutting: what the Google Maps Platform Terms of Service and Service Specific Terms say about exporting, caching, extracting, storing offline, or creating derivative datasets (applies to Map Tiles, Solar, Elevation, Aerial View)

### Takeaway
The Google Maps Platform ToS (last modified Aug 26, 2026) flatly prohibits exporting/extracting/scraping "Google Maps Content" (defined to include "map and terrain data, imagery") for use outside the Services, prohibits any caching not expressly permitted by the Service Specific Terms, and prohibits "creating content" from Google Maps Content — its own examples include building "3D building models" from imagery and "terrain models based on elevation values from the Elevation API". The Service Specific Terms (last modified June 10, 2026) grant only narrow caching windows (e.g., 30 days for Solar API data) and contain no export/caching allowance at all for the Map Tiles API.

### Inferences
- Converting any Google Maps Platform 3D mesh, DSM raster, or elevation samples into a DWG/DXF that lives in AutoCAD is, on the plain wording, (1) an "export/extract" of Google Maps Content "for use outside the Services" (§3.2.3(a)), (2) "storing" it (§3.2.3(a)(i)) beyond any permitted caching window (§3.2.3(b)), and (3) "creating content based on Google Maps Content" (§3.2.3(c)) — the ToS's own examples ("create 3D building models", "build terrain models based on elevation values") describe exactly this workflow.
- Because the Map Tiles API has no Service Specific Terms caching allowance, the default rule of §3.2.3(b) ("will not cache … except as expressly permitted") applies with no exception; the Map Tiles API Policies page (see next section) adds product-specific prohibitions on top.

## Key Question 1: Google Map Tiles API "Photorealistic 3D Tiles" — format, access mechanics, and what the Map Tiles API Policies + ToS say about downloading/converting tiles to a mesh

### Takeaway
Photorealistic 3D Tiles are Google Earth's photogrammetric mesh served as OGC 3D Tiles (glTF/GLB tiles, Draco-compressed) from `https://tile.googleapis.com/v1/3dtiles/root.json?key=…` with a session token; they are meant to be streamed into a renderer (CesiumJS, deck.gl, Three.js/3DTilesRendererJS, Unity/Unreal via Cesium). Technically anyone with a key can pull the .glb tiles into Blender/Rhino (tools exist), but Google's Map Tiles API Policies — as quoted by multiple independent implementers — forbid pre-fetching/storing/caching, forbid "non-visualization use cases" including "geodata extraction" and "offline uses", and state that 3D objects may not be "extracted, traced, or otherwise derived by hand or machine from Photorealistic 3D Tiles"; the ToS's no-scraping/no-derivative-content clauses apply on top.

### Cited Findings
Format and access mechanics:
- Google release note (effective June 9, 2025): "3D Tiles will continue to be in the Open Geospatial Consortium (OGC) standard glTF format, and renderer implementations must continue to support the OGC glTF specification." and "root.json will now contain the root tile itself, instead of a link to the root tileset, so moving forward, one HTTP request will be required to begin traversing the tree, instead of two." — [Map Tiles API release notes](https://developers.google.com/maps/documentation/tile/release-notes) (search-result snippet; page not directly fetchable)
- Session tokens: "The session parameter is a built-in identifier for a 3D loading session that's automatically generated by the API and must be attached by the renderer when constructing subsequent tile requests." and "A single root tileset request allows for at least three hours of tile requests before requiring a new request." — [Photorealistic 3D Tiles docs](https://developers.google.com/maps/documentation/tile/3d-tiles) / [Work with a 3D Tiles renderer](https://developers.google.com/maps/documentation/tile/use-renderer) (search-result snippets)
- Root endpoint used by CesiumJS: "`${GoogleMaps.mapTilesApiEndpoint}v1/3dtiles/root.json`"; the JSDoc also states "Google Photorealistic 3D Tiles can only be used with the Google geocoder." — [CesiumGS/cesium createGooglePhotorealistic3DTileset.js](https://github.com/CesiumGS/cesium/blob/main/packages/engine/Source/Scene/createGooglePhotorealistic3DTileset.js)

### Inferences
- The API does not give "a different kind of access to Google Earth": it streams the same photogrammetric mesh Google Earth renders, as OGC 3D Tiles for live visualization, under terms that are stricter (session-scoped, no storage, no derivation) than the consumer Google Earth product.

## Key Question 2: Google Solar API — dataLayers (DSM GeoTIFF), buildingInsights (roof-segment geometry), terms on storing/reusing, coverage, pricing

### Takeaway
The Solar API is the one Maps Platform product that hands you actual height data as files: `dataLayers:get` returns time-limited URLs to GeoTIFFs including a 0.1 m/pixel Digital Surface Model (meters above EGM96), RGB, building mask, annual/monthly flux and hourly shade, for a radius up to 100 m (more with coarser pixels, ≤175 m if you want monthly/hourly layers); `buildingInsights:findClosest` returns per-roof-segment pitch, azimuth, plane height at center, center point and bounding box. But the Service Specific Terms restrict use to solar-energy feasibility/design/downstream transactions and cap caching of "Solar Data" at 30 days (except when baked into fixed media for a solar Downstream Transaction) — so importing the DSM into AutoCAD for general site design is outside the licensed purpose.

### Cited Findings
dataLayers endpoint (verbatim from Google's Solar API discovery document, revision 20260922):
- Method: "v1/dataLayers:get — Gets solar information for a region surrounding a location. Returns an error with code `NOT_FOUND` if the location is outside the coverage area." — [Solar API discovery doc](https://solar.googleapis.com/$discovery/rest?version=v1)
- `radiusMeters`: "Required. The radius, in meters, defining the region surrounding that centre point for which data should be returned. The limitations on this value are: * Any value up to 100m can always be specified. * Values over 100m can be specified, as long as `radius_meters` <= `pixel_size_meters * 1000`. * However, for values over 175m, the `DataLayerView` in the request must not include monthly flux or hourly shade." — [Solar API discovery doc](https://solar.googleapis.com/$discovery/rest?version=v1); same text on [dataLayers.get reference](https://developers.google.com/maps/documentation/solar/reference/rest/v1/dataLayers/get) (search snippet)

## Key Question 3: Google Elevation API — resolution, sampling limits, terms on storage

### Takeaway
The Elevation API returns interpolated point elevations (meters) plus a "resolution" value meaning the maximum spacing of the source samples; Google's own client-library documentation notes the data gets coarser when many points are requested. The ToS explicitly prohibits bulk-downloading "elevation values" and building "terrain models based on elevation values from the Elevation API", and the Service Specific Terms grant no caching allowance for it.

### Cited Findings
- Google's official JS client (googlemaps/google-maps-services-js) documents the response: "An `elevation` element indicating the elevation of the location in meters." and "A `resolution` value, indicating the maximum distance between data points from which the elevation was interpolated, in meters. This property will be missing if the resolution is not known. Note that elevation data becomes more coarse (larger `resolution` values) when multiple points are passed. To obtain the most accurate elevation value for a point, it should be queried independently." — [googlemaps/google-maps-services-js src/elevation.ts](https://github.com/googlemaps/google-maps-services-js/blob/master/src/elevation.ts); same wording in Google's Java client [ElevationResult.java](https://github.com/googlemaps/google-maps-services-java/blob/main/src/main/java/com/google/maps/model/ElevationResult.java)
- Official overview page (not fetchable): [Elevation API overview](https://developers.google.com/maps/documentation/elevation/overview); requests page: [Elevation requests and responses](https://developers.google.com/maps/documentation/elevation/requests-elevation)
- ToS prohibits "bulk download [of] ... elevation values" (§3.2.3(a)(ii)) and "build[ing] terrain models based on elevation values from the Elevation API" (§3.2.3(c)(iii)) — [Google Maps Platform ToS §3.2.3](https://cloud.google.com/maps-platform/terms)
- The Service Specific Terms have no Elevation API section (no caching permission) — [Service Specific Terms](https://cloud.google.com/maps-platform/terms/maps-service-terms)
- Elevation API is a listed Core Service — [Core Services Summary](https://cloud.google.com/maps-platform/terms/maps-services)

### Inferences
- A parcel-scale terrain surface in AutoCAD built from Elevation API samples is the textbook example the ToS uses of prohibited "creating content"; even setting terms aside, the interpolated "resolution" field means it is not survey-grade.

### Gaps
- Per-request limits (e.g., number of locations / path samples per request), the underlying data sources and their resolutions, and current pricing/free tier were not verifiable from an official page in this session (developers.google.com blocked; search snippets only described competitors' APIs).

## Key Question 5: Google Earth Engine — which elevation datasets are exportable, licensing, commercial pricing

### Takeaway
Earth Engine is the one Google channel that legitimately yields exportable height rasters for a US parcel: it hosts public-domain USGS 3DEP 1 m and 10 m DEMs (bare-earth), NASADEM/SRTM 30 m and Copernicus GLO-30, and its API has `image:export`/`computePixels` that write GeoTIFFs to Drive/Cloud Storage. ## Key Question 6: Google Earth Pro (desktop) and Google Earth (web) — can they export 3D buildings/terrain; what can be exported; history of the SketchUp/3D Warehouse pipeline

### Takeaway
Neither Google Earth Pro nor Google Earth web offers a 3D building/terrain mesh export; Google Earth Pro exports user-authored KML/KMZ (placemarks, paths, polygons, folders), images and movies. Google's new commercial "Google Earth" Service Specific Terms (2026) allow downloading the user's own designs "as a KMZ or PNG" but forbid downloading/exporting Google's data layers and state design features "should not be used for construction or structural engineering designs". The only era in which building geometry was openly downloadable was the SketchUp/3D Warehouse user-model pipeline, which Google retired on October 1, 2013 in favor of auto-generated photogrammetry.

## Key Question 7: Has Google licensed the 3D mesh to partners (Cesium ion, Esri) and what restrictions apply there

### Takeaway
Google distributes Photorealistic 3D Tiles through Cesium ion (since Oct 2023, keyless via Cesium ion asset 2275207 when no Google key is set) and, from 2025, into Esri ArcGIS — but in both cases as streamed visualization under Google's terms (attribution/logo, no caching beyond what the asset allows, no offline/export), not as a licensed dataset for derivative use.

## Key Question 8: 2025–2026 changes (new features, licensing, export policies)

### Takeaway
Between 2025 and September 2026 the relevant changes were: the March 1, 2025 pricing overhaul (per-SKU free tiers replacing the $200 credit; Photorealistic 3D Tiles = Enterprise SKU with 1,000 free root requests), the June 9, 2025 3D Tiles protocol change (root.json carries the root tile) and a large quota increase, an EEA cut-off for new 3D Tiles projects (July 8, 2025), Esri's ArcGIS integration (2025), a Map Tiles policy refresh reported around June 29, 2026 that keeps the ban on machine extraction, "Google Earth" being added to Maps Platform Core Services with its own no-export terms, Solar API "EXPANDED_COVERAGE" pre-GA experiments, and Earth Engine noncommercial EECU tiers from April 27, 2026. Nothing found relaxes export of 3D data.
