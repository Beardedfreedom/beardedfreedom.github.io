Cloud Sessions

Claude Code on a VM that isn't your laptop. Close the lid and the session keeps working; steer it from a browser, your phone, the desktop app, or claude itself. Anthropic did publish this one — it's just long. Here it is compressed, with the sharp edges flagged.

01 · tl;dr

The 60-second version

  • Same agent, different iron. A cloud session is a Claude Code session running on cloud infrastructure — an Anthropic-managed VM by default, or your org's self-hosted environment when it's routed there.
  • Five ways in. claude.ai/code (a.k.a. Claude Code on the web), the Code tab in the Claude mobile app, the desktop app with Cloud picked instead of Local, claude --cloud in a terminal, and routines — every scheduled or triggered run is its own cloud session.
  • Every session runs in an environment — a saved config for network access, env vars, and a setup script. Onboarding leaves you a Default one with Trusted network access, and the same environments apply whichever surface launched the session.
  • GitHub is the wire. The VM clones your remote. It never sees your disk unless you're in bundle mode (§04).
  • No meter on the VM. There's no separate compute charge — but sessions draw from the same rate limits as the rest of your Claude and Claude Code usage, and parallel sessions draw proportionally faster.
  • Who gets it. Pro, Max, and Team plans, plus Enterprise users on premium or Chat + Claude Code seats. Not orgs with Zero Data Retention, and not through Bedrock, Google Cloud's Agent Platform, or any other third-party provider.
  • Herding a dozen? A project is one conversation where Claude starts and tracks many cloud sessions for a single body of work.
02 · handoff map

What moves, and which way

The CLI starts new cloud sessions, messages running ones, and drags one down to your terminal. What it can't do is push a session that's already running locally up to the cloud.

Handoff moves
movehowwhat actually happens
terminal → cloud, new claude --cloud "task" A fresh session for the current repo. The VM clones your GitHub remote at your current branch — unpushed commits don't exist up there. Setup streams as a live checklist; anything you type while it provisions gets queued.
terminal → cloud, running claude -p "msg" --cloud <id> Queues one message and exits — no reply, no local session state sent. Works from any machine signed in with claude auth login, in any shell (PowerShell too).
cloud → terminal claude --teleport [<id>] Checks the repo, fetches and checks out the session's branch, loads the full transcript. From then on it's a fork: local work stays local (§06).
local → cloud, running desktop app → Continue in The one sanctioned way to send an existing local session up. Not a CLI feature.
phone / web → local /remote-control Not a cloud session at all — you steer a session that's still running on your machine. Handy right after a teleport.
name collision --remote is the deprecated spelling of --cloud and still works. --remote-control is an unrelated feature that keeps everything on your machine. Don't let tab-completion pick for you.
03 · command sheet

Paste-ready commands

# ship a task (push first — it clones the remote, not your disk)
$ claude --cloud "Fix the race in src/queue/worker.ts"

# plan locally, execute remotely
$ claude --permission-mode plan
#   …save the plan to docs/plan.md, commit, push…
$ claude --cloud "Execute the plan in docs/plan.md"

# fan out: every --cloud call is its own independent session
$ claude --cloud "Deflake tests/auth.spec.ts"
$ claude --cloud "Regenerate the API reference"

# steer a running session from anywhere (queues one message, exits)
$ claude -p "also update CHANGELOG.md" --cloud session_01AbCd…
$ echo "run the linters again" | claude -p --cloud claude.ai/code/session_01AbCd…

# same send, machine-readable
$ claude -p "status?" --cloud <session-id> --output-format json

# no remote, no GitHub App on the repo, or you just want to: upload a bundle
$ CCR_FORCE_BUNDLE=1 claude --cloud "Run the suite and fix failures"

# pull a cloud session down into this checkout
$ claude --teleport                # picker
$ claude --teleport <session-id>   # straight to it
# inside a local Claude Code session
/teleport     # or /tp: same picker, no restart
/tasks        # then press t on a background session to teleport into it
/autofix-pr   # on a PR's branch: spawn a cloud session with auto-fix armed
  • Session IDs can be the bare session_… or cse_… form, or the session's claude.ai/code/<id> URL — scheme and query string optional.
  • A good send prints Sent to cloud session., the session ID, and a View: link. With --output-format json you get {ok, session_id, url} instead.
  • One repo per call. --cloud works on a single repository at a time.
  • Done up there? Open a PR from claude.ai/code, or teleport the session down and keep going locally.
04 · what the vm sees

It clones. Sometimes it bundles.

Clone from GitHub

  • The VM clones your repo's GitHub remote at the branch you're on.
  • Unpushed commits and uncommitted edits? Invisible. Push first.
  • Work goes back up as a pushed branch; open a PR from claude.ai/code when it's done.

Upload a bundle

  • Kicks in when the repo has no git remote, or it's a github.com repo the Claude GitHub App isn't installed on — even if you connected through /web-setup. Force it with CCR_FORCE_BUNDLE=1.
  • Ships full history across every branch, plus uncommitted changes to tracked files. Untracked files stay home — git add what the session needs.
  • Needs a git repo with at least one commit.
  • Pushes back to GitHub only if your GitHub connection has push access there. GitLab, Bitbucket and friends can bundle in, but can't push back.

The 100 MB ladder

  1. Whole repo — full history, every branch — if the bundle comes in under 100 MB.
  2. Too big? Current branch only.
  3. Still too big? One squashed snapshot of the working tree.
  4. Still too big? The send fails.
secrets & bundles

On macOS, Linux, and WSL, uncommitted changes to files that look like credentials — .env files, Terraform *.tfvars, keys like id_rsa and *.pem — are held back from the upload, and the CLI names what it skipped. The session gets the committed version, or no file at all.

What that filter doesn't cover: linked worktrees, submodules, and similar layouts (there those changes upload with everything else, and the CLI names them instead); platforms beyond the three the docs list; and anything already committed. A secret that ever landed in a commit is in history — and by default, history ships.

06 · teleport

Teleport preflight

Four checks run before a cloud session lands in your terminal. Clear them up front and it's one command.

  • Clean tree. No uncommitted changes — teleport offers to stash them for you.
  • Same repo, not a fork. Run it from a checkout of the session's repository. Get it wrong and the error names the session's repo — and, since v2.1.219, yours too. A remote it can't parse into a hostname (an SSH alias like git@work:owner/repo.git) gets a confirm prompt, and passes when owner and repo name match.
  • Branch pushed. The session's branch has to be on the remote; teleport fetches and checks it out itself.
  • Same account, subscription auth. Signed in to the claude.ai account that owns the session. API-key auth doesn't cut it — run /login.

Five ways to jump

  • claude --teleport for a picker, or claude --teleport <id> to go straight there.
  • /teleport (or /tp) inside a running CLI session — same picker, no restart.
  • /tasks, then t on a background session.
  • On claude.ai/code: session menu → Open in → Terminal copies the command.
  • Inside the cloud session itself, /teleport replies with the exact claude --teleport <id> line to run from a checkout (v2.1.223+ in the session's environment).
fork, not sync

Teleport gives your terminal its own copy of the session. Nothing you do locally shows up in the cloud session on the web or your phone. Want pocket control back? Run /remote-control in the local session. And don't reach for --resume: it only reads this machine's local history and never lists cloud sessions.

07 · in-session

Slash commands, up there

Commands that print text work. Commands that need the terminal UI don't, and pickers turn into arguments.

Slash commands in cloud sessions
commandin the cloudnotes
/compact [focus] yes focus text is optional: /compact keep the test output
/context yes shows what's in the context window
/clear no start a new session from the sidebar instead
/model /effort /color /rename argument form /model sonnet — no picker, no slider. Needs v2.1.205+ in the session's environment
/fast toggle when fast mode is available on your account. Needs v2.1.271+
/config opens settings in the browser it opens the Claude Code settings page; anything after the command, key=value included, is ignored
/plugin /resume no terminal-UI only
  • Settings live elsewhere. Set environment variables on the cloud environment, or — in a single-repo session — commit the key to that repo's .claude/settings.json.
  • Compaction fires early, on purpose. Cloud sessions set CLAUDE_AUTOCOMPACT_PCT_OVERRIDE themselves, so compaction triggers partway through the auto-compact window instead of at the brim, and their value beats any you put in the environment. To move the goalposts, change the window instead: CLAUDE_CODE_AUTO_COMPACT_WINDOW, or /autocompact <tokens> when that variable isn't set.
  • Subagents work exactly as they do locally, and the repo's .claude/agents/ is picked up automatically. Agent teams are off by default — add CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1 to the environment's variables.
  • Permission mode comes from the mode dropdown, at launch or mid-run. Reopen a session whose environment expired and it resumes in the mode it was in.
  • Review in place. The +42 -18 badge opens a diff against the base branch (or any other branch, via Compare against). Inline comments on lines ride along with your next message.
  • Unsend. A message sent mid-run queues; click its ✕ and the text drops back into the box — unless Claude already read it.
  • Walk away mid-question. If Claude asks something and you vanish, answer whenever — up to environment expiry — and it picks up from your answer.

09 · auto-fix

Auto-fix: the PR babysitter

Claude subscribes to a pull request's GitHub activity. When a check goes red or a reviewer comments, it investigates and pushes a fix if one is clear. Requires the Claude GitHub App on the repo.

  • PR born in a cloud session: open it at claude.ai/code → CI status bar → Auto-fix.
  • Terminal: /autofix-pr on the PR's branch. It finds the PR with gh, spawns a cloud session, and arms auto-fix in one step.
  • Phone: just ask — "watch this PR and fix any CI failures or review comments."
  • Any PR: paste its URL into a session and ask.

It's a per-PR toggle. Disarm it from the same CI status bar, or tell Claude to stop watching.

  • Clear fix that doesn't clash with earlier instructions → change, push, explain in the session.
  • Ambiguous or architectural → asks you first.
  • Duplicate or no-op → notes it, moves on.
  • Merge conflicts → invisible. GitHub sends no webhook when the base branch moves and creates a conflict, so open the session and ask for a rebase.

Thread replies post under your GitHub account, labeled as Claude Code.

loaded trigger

If a PR comment can run something — Atlantis, Terraform Cloud, a GitHub Action on issue_comment — then Claude's replies, posted as you, can pull that trigger. Audit the repo's automation before arming auto-fix, and leave it off anywhere a comment can deploy infrastructure or run privileged operations.

10 · threat model

Isolation, and where it ends

  • One VM per session, isolated and Anthropic-managed. Routed to a self-hosted environment instead? Then isolation is your deployment's job.
  • Egress is limited by default and can be switched off entirely — but even with network access disabled, Claude Code still talks to the Anthropic API, and that channel can carry data out of the VM. Self-hosted, you restrict egress at your own boundary.
  • Git credentials and signing keys never enter the sandbox. A proxy outside it authenticates for the session with scoped credentials. Self-hosted deployments supply their own git credentials.
  • API keys you add to an environment (Pro and Max, Anthropic-hosted) stay outside the sandbox too, attached to matching requests after they leave the session. Not available on self-hosted environments, and not yet on Team or Enterprise.
  • Code is analyzed and modified inside the session's isolated environment before any PR gets created.

Sharing a session

Private or Public — and public means any logged-in claude.ai user. Repo-access verification is off by default. Sessions can hold code and credentials from private repos, so scrub before you flip it. Settings → Claude Code → Sharing settings can require repo access and hide your name.

Private or Team (your claude.ai org). Repo-access verification is on by default, checked against the GitHub account connected to each recipient's account. Your display name is visible to everyone with access. Claude in Slack sessions are Team-visible automatically.

Shared links show the latest state when opened — not a live feed. Archiving hides a session from the default list; deleting it (after a confirm) is permanent.

11 · error decoder

Error decoder

The strings you'll actually see, what they mean, and the fix.

  • CLI errors are prefixed Error: ; a failed send is wrapped as failed to send message to cloud session <id>: <reason>.
  • With --output-format json, send failures come back as {ok: false, session_id, error} — but configuration errors (wrong provider, policy off) go straight to stderr, no JSON. stream-json isn't supported with --cloud <id>.
Cloud sessions aren't available with <provider>. They run on Anthropic's infrastructure and require an Anthropic account.
means
Claude Code is configured for a third-party provider. The message uses your config's label, e.g. Amazon Bedrock or Google Vertex AI.
fix
Remove that provider's config (e.g. unset CLAUDE_CODE_USE_BEDROCK), then claude auth login. A gateway set only through ANTHROPIC_BASE_URL doesn't trip this, but you still have to log in.
Cloud sessions are disabled by your organization's policy. Contact your organization admin to enable them.
means
The org's allow_remote_sessions policy is off.
fix
An Owner turns it on in the Claude Code admin settings at claude.ai/admin-settings/claude-code.
Couldn't verify your organization's policy for cloud sessions. Check your network connection and try again.
means
The policy fetch failed, so the CLI fails closed instead of assuming yes.
fix
Fix the network, retry.
Attaching to an existing cloud session is not enabled for your account.
means
You ran --cloud <session-id> without -p.
fix
claude -p "your message" --cloud <session-id>
Session not found: <id>
means
That ID or URL doesn't match a session you can access.
fix
Re-copy it from the session's claude.ai/code URL.
cloud session <id> is archived and cannot accept new messages
means
Archived sessions don't take new messages.
fix
Start a new session.
Unable to get organization UUID · Error loading Claude Code sessions
means
--cloud and --teleport need a claude.ai sign-in, and you're on API-key auth or your stored account details are stale. You may instead see a note that API key authentication is not sufficient; a bare claude --teleport shows the second string in its picker.
fix
/login with your claude.ai account, then retry.
Remote Control session expired · Access denied
means
Teleport rides the same Remote Control infrastructure as cloud sessions, so its auth errors use that wording. The connection token is short-lived and scoped to your account.
fix
/login to refresh, reconnect, and confirm you're on the account that owns the session.
Remote Control may not be available for this organization
means
An Owner hasn't enabled cloud sessions for your org.
fix
Ask an Owner.
Session creation failed
means
No VM could be allocated. Same story if it stalls at provisioning.
fix
Check status.claude.com, retry after a minute (capacity is provisioned on demand), and confirm your GitHub connection can actually see the repo.
[ environment expired ]
means
The session sat idle and its VM was reclaimed. Waiting on you to approve an MCP connector tool call, or to sign in to an MCP server, counts as idle.
fix
Reopen it from claude.ai/code: fresh VM, conversation restored. Background subagents and shell commands that were mid-run don't come back.
API Error: 500 · 529 Overloaded · 429 · Prompt is too long
means
Runtime API errors, shared with the CLI and desktop app. Not cloud-specific.
fix
See the official error reference.
12 · hard limits

Hard limits

  • Rate limits are shared. Cloud sessions draw from the same pool as all your other Claude and Claude Code usage, and parallel sessions burn through it proportionately faster. There's no separate compute charge for the VM itself.
  • GitHub or bust, for pushing. Cloning and PR creation require GitHub; GitHub Enterprise Server works on Team and Enterprise plans. Other hosts can go up as a bundle via CCR_FORCE_BUNDLE=1, but results can't be pushed back to that remote.
  • Same account to pull. You can only teleport a session down while signed in to the account that owns it.
  • Org IP allowlists break it. Anthropic-hosted sessions call the API from Anthropic's infrastructure, not your network, so with IP allowlisting on, every one of them fails auth — Code Review and routines on Anthropic-hosted environments too. Self-hosted environments call from your own network. The fix is asking Anthropic support to exempt Anthropic-hosted services.
  • Your diff drivers don't run. Session diffs are computed from raw git blob content, so textconv filters and custom diff drivers are ignored.
  • Idle means reclaimed. See environment expired in the decoder.
